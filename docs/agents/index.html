For agents

Building mdk apps with an agent

Every page of these docs has a plain-text twin, the repo ships a skill, and the CLI prints the whole API as JSON. An agent can build, run and visually verify an mdk app without a human in the loop.

Hand it to your agent

Use mdk for this desktop app: read https://javimosch.github.io/machin-desktop/llms.txt and follow it.

Paste that into Claude Code, Devin, Codex or any coding agent. The site index links each page's own llms.txt, so the agent fetches only what the task needs.

The loop an agent should run

./mdk guide                                   # learn the API (JSON)
./mdk new apps/thing                          # scaffold
# … edit apps/thing/app.src …
./mdk check apps/thing                        # typecheck (fast, no window)
./mdk shot apps/thing /tmp/t.ppm --click 120 80 --click 120 80
convert /tmp/t.ppm /tmp/t.png                 # LOOK at the result
./mdk build apps/thing -o thing               # ship

The screenshot step is the one agents skip and shouldn't: --click sends real SDL events through the normal input path, so a screenshot after clicks proves the interaction, not just the first frame.

Contract

  1. An app is a directory of .src files. mdk prepends framework/*.src and compiles them together with machin (encode concatenates files: that is the module system).
  2. Define exactly one func view(). It runs every frame that needs drawing (input, resize, reload, or animate()).
  3. Do not define main(). The framework exports mdk_frame, which wraps view() in arena { } so a frame's temporaries are freed when it returns.
  4. Keep state in the host store: state_int/set_int, state_f/set_f, state_str/set_str. It survives every hot reload; MFL globals do not (they reset on reload).
  5. Never assign per-frame values to MFL globals: inside the frame arena, a global assignment promotes the value out of it and leaks every frame. Assigning a global once (a cache filled on first frame) is fine.
  6. Build the UI top-down every frame: open containers with col()/row(), add content, close with end(). Modifiers (gap, bg, pad, ...) apply to the LAST created element, or to the container just closed by end().
  7. Widgets return their event for this frame: if button("Save") { ... }.

Gotchas

  • machin typechecks reachably: an error in a function view() never calls does not fail the build (and draws no overlay).
  • MFL loops are while cond { }; there is no C-style for. Floats need a dot (16.0); int->float is float(i).
  • Struct types are type T struct { ... } with one field per line.
  • Colors are ints 0xRRGGBBAA; the alpha byte matters (0x...00 is invisible).
  • Modifiers apply to the last element: call them right after the element (or right after end() for a container).
  • Text is clipped by nothing yet: keep content inside the window, or use vlist for long lists.
  • To verify without a human: ./mdk shot <app> out.ppm --click X Y, then convert out.ppm out.png and look at it.

Why this matters

machin itself is designed for agents to write cheaply — zero type annotations, one declaration per line, a machin guide that documents the language as JSON. mdk keeps that promise for desktop UIs: one language for the whole app, a typechecker in front of every reload, an immediate-mode API with no callbacks or retained widget objects to keep in sync, and a verification loop that needs no human.
